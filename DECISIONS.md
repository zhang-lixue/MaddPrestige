# MaddPrestige V2 Decision Log

**Owner approval recorded:** 2026-08-15
**Status legend:** `Mandated` comes directly from the master specification; `Owner-approved` was explicitly approved by the owner; `Deferred` is intentionally unresolved until its named phase/evidence exists.

| D-014 | Mandated | QuickShop and other P2P volume provide zero progression-income credit by default. | Prevents circular/collusive turnover exploits. |
| D-015 | Owner-approved | Internal state uses immutable lowercase IDs limited to the conservative `a-z0-9._-` syntax, exact decimal currency storage, optimistic state revisions, and normalized history/baseline/operation records. | Decouples display/external IDs and protects integrity. |
| D-016 | Owner-approved | Consequential changes use immutable operation plans with persisted per-action state, idempotency keys, verification, and reconciliation. | Provides crash recovery without falsely promising exactly-once external commands. |
| D-017 | Owner-approved | SQLite is the default single-server backend and uses a serialized bounded write coordinator. MySQL and MariaDB may implement the same contracts, but each requires contract testing if publicly claimed. | Backend support does not imply multi-server/network-safe progression. |
| D-018 | Owner-approved | Database migrations are ordered/checksummed, backup-gated, dry-runnable, and reported; schema versions are never overwritten opportunistically. | Fixes current version-4 false-current risk. |
| D-019 | Owner-approved | Staff observation, draft edit, apply, rollback, player mutation, force, migration, recovery, and debug have separate permissions. | Removes GUI privilege escalation and supports least privilege. |
| D-020 | Owner-approved | PAPI output is cache-only; PAPI input is a separately configured sampled/typed provider that fails closed. | Protects render performance and makes outages actionable. |
| D-021 | Owner-approved | Generic command actions are disabled in the safe default, require explicitly allowlisted roots/templates, and expose uncertainty honestly. | A denylist cannot make arbitrary console commands safe; universal exactly-once behavior is not claimed. |
| D-022 | Mandated | Rabbit Holes, decrees, bosses, resource-world lifecycle, Court drafting, and PvP scoring are not core mandatory progression systems. | They may be future optional providers only. |
| D-023 | Owner-approved | Phase 1 builds foundations only and never touches production data or existing schema except disposable fixtures. | Preserves the Phase 0/1 safety gate. |
| D-024 | Owner-approved | Maven group is `net.maddkraft`; Java root package is `net.maddkraft.maddprestige`. | The developer/product namespace may carry MaddKraft identity, but generic core gameplay remains unbranded and configuration-driven. |
| D-025 | Owner-approved | Use the canonical file split proposed in Phase 0. | Avoids a monolithic configuration while preserving one canonical model. |
| D-026 | Owner-approved | Network/proxy synchronization is outside V2 core unless separately designed and qualified. | MySQL/MariaDB availability must not be advertised as network-safe progression. |
| D-027 | Owner-approved | Competitions are disabled in the generic default; a generic optional module may exist, while MaddKraft competition identity is deferred. | Removes hardcoded MaddHatter behavior from core. |
| D-028 | Owner-approved | Retention is configurable; revisions/backups/migration artifacts referenced by active or pending work are protected from pruning; secrets are redacted from every output surface. | Phase 1 establishes policy/schema, with user-facing tuning later. |
| D-029 | Owner-approved | Persistence must support documented player-data inventory, export, safe deletion/anonymization, and history/audit retention without breaking referential integrity. | Public-facing tooling is primarily Phase 8, but the storage model must enable it. |
| D-030 | Owner-approved | Do not infer legacy rank mappings. If no production data exists, freeze available V1 artifacts and use synthetic edge-case migration fixtures; real data elsewhere remains untouched and must be backed up before later migration work. | Lack of a production fixture does not block Phase 1 foundations. |
| D-031 | Phase 1 implementation | Select SnakeYAML Engine 3.0.1 for YAML 1.2 parsing/marks and a MaddPrestige-owned lossless source document for narrow scalar edits. Every edit reparses; block scalars, anchored scalars, and explicitly tagged scalars fail closed. | Hardened golden/regression tests prove comments, order, dotted/nested/unknown keys, CRLF, supplementary Unicode, safe quoting, scalar styles, and multiple documents without trusting a destructive whole-document emitter. |
| D-032 | Phase 1 implementation | The root becomes the seven-module Maven parent; the distribution module compiles unchanged V1 sources/resources/tests from their original root paths and bundles inactive V2 foundations. | Establishes approved modules without a big-bang V1 move or activating V2 against live data. |
| D-033 | Phase 1 implementation | SQLite is the only locally implemented/tested V2 backend. MySQL 8.4.10 and MariaDB 11.8.8 CI definitions are contract harness targets only and are not support claims. | Local Docker/services are absent; compilation or primitive CI probes cannot establish full repository/backend compatibility. |
| D-034 | Phase 1 implementation | The verified byte-copy backup service is restricted to quiesced/disposable files. Live SQLite WAL backup requires a later coordinated online-backup/checkpoint implementation and remains fail-closed. | Avoids presenting a byte copy of an active WAL database as a production-safe backup. |
| D-035 | Phase 1 correction | SQLite migration preflight is read-only; required verified backup precedes migration-history DDL. Only `APPLIED` versions are unique through a partial index, failed attempts remain repeatable, and applied history must be an exact prefix of the requested chain. | Preserves the backup-first invariant, auditability, safe retry, deterministic ordering, and protection against running an older missing migration after newer history. |
| D-036 | Phase 2 implementation | `progression.yml` is compiled through the Phase 1 canonical draft/revision service into an immutable ordered stage snapshot. Fresh defaults are inactive; active deferred Phase 3+ fields fail validation. | Adds arbitrary stages without a second configuration system or misleading placeholder gameplay behavior. |
| D-037 | Phase 2 implementation | One rank adapter may project an ordered ladder in Phase 2; individual stages may use `projection: none`. Configuration candidates pin the externally validated provider generation, and every operation pins the complete managed group set, desired projection, config revision, and provider generation. | Keeps baseline behavior configurable while making validation/apply/reload races and ownership scope explicit. Multi-adapter ladders remain unsupported rather than partially activated. |
| D-038 | Phase 2 implementation | LuckPerms ownership is limited to exact permanent, context-free direct inheritance nodes in the revision-pinned managed set. Contextual/temporary managed nodes are ambiguous and preserved; every configured target is loaded/validated before mutation. | Enforces the narrowest provable ownership boundary and prevents a bad target from stripping prior managed membership. |
| D-039 | Phase 2 implementation | UUID-first player stage state uses optimistic revisions. Authoritative repairs use persisted operation/action state; save or mid-generation uncertainty becomes `NEEDS_RECONCILIATION`. Import-once inserts only an absent internal record from one unambiguous mapped group. | Prevents display/order drift, feedback loops, stale writes, blind replay, and false success. |
| D-040 | Phase 2 owner-review correction | A revisioned stage remap plan records intent but never proves player rows were remapped. While removed/disabled stages have nonzero stored references and Phase 2 has no atomic remap executor, configuration activation remains blocked even when the plan is complete. | Preserves authoritative player-stage referential safety without pulling production bulk migration into Phase 2. |
| D-041 | Phase 3 implementation | Requirement values are provider-advertised typed metrics; trees reference immutable requirement IDs and baseline/latch identity uses the versioned `rsf2:` SHA-256 of a deterministic length-prefixed binary encoding of every behavioral field. | Prevents permissive string coercion, structurally ambiguous filter serialization, and a changed operator/target/scope/scaling/catch-up policy inheriting stale completion state. |
| D-042 | Phase 3 implementation | Requirement evaluation is pure. Lifecycle services initialize baselines and persist eligible latches explicitly at owned boundaries using UUID, measurement scope, scope-instance ID, semantic fingerprint, and provider generation; returned records must match the exact requested key. | Simulation/repeated reads cannot mutate progress, while stage/prestige/season instances remain isolated and resettable without deleting unrelated history. The services and persistence semantics are tested, but no production Phase 3 lifecycle owner invokes them yet; future stage-runtime composition owns stage entry/completion calls and Phase 4 owns Prestige/season calls. |
| D-043 | Phase 3 implementation | Scaling is applied before opt-in catch-up. Linear, exponential, and stepped formulas use exact decimal arithmetic with explicit index, parameter precision/scale, predicted exponential precision-work/magnitude, final magnitude, rounding, and quantum bounds; catch-up reduction is capped and floored. | Makes targets deterministic/auditable and rejects pathological `BigDecimal.pow` work before computation without clamping. |
| D-044 | Phase 3 implementation | Only the canonical rank-up authorization service may issue executable authority. Public `RankUpIntent` carries actor/player/optional target/idempotency intent only; engine-injected progress-context and requirement-state sources own scaling, catch-up, scope identity, baselines, and latches. Authorization resolves the legal next enabled stage and exact tree/costs/rewards from the atomic active snapshot. A plan separately binds the player's observed source-state config provenance and the current active config revision governing the operation; successful commit CAS-checks the former and writes the latter. Configured rank projection must be active, generation-pinned, healthy, and implement `RankAdapter` during planning/simulation. A blocked canonical plan carries denied authority. An executable seal binds identity/stages/revisions/provider generations, complete requirement result and provenance, costs/rewards, configured and requested projection, blockers/execution allowance, and the operation plan; diagnostic-only unavailable-provider reporting is not consumed by execution and is deliberately outside the seal. Execution validates the seal before persistence, then orders costs → external projection → optimistic internal commit → rewards. | Prevents caller-fabricated progress state, safe config applies freezing unchanged player stages, inaccurate simulation during rank-provider outage, blocked-plan escalation, requirement-outcome or projection substitution, fabricated/stale evaluations, skipped actions/stages, partial effects, false success, and unsafe replay. External-first ordering makes external-success/internal-failure explicit; the inverse cannot be created by this executor and existing reconciliation handles preexisting divergence. |
| D-045 | Phase 3 implementation | Authorized command rewards use reviewed templates and structured exact tokens. Policy is disabled by default, normalizes roots, applies mandatory dangerous-root precedence, enforces operation-wide count/length bounds, and checks maximum recursion against a trusted runtime `CommandExecutionContext` whose correlation is retained and whose nested depth can only increase. Commands remain non-idempotent/non-reversible with external uncertainty. | Prevents configuration metadata from claiming a false trigger depth and avoids turning configuration into arbitrary console, shell, SQL, filesystem, reflection, or code execution. Phase 3 proves context propagation at the provider boundary; production command-triggered rank-up ingress remains Phase 6. |
| D-046 | Phase 3 implementation | Vanilla statistics are discovered from the real Bukkit API, advertise separately classified block/item/entity dimensions, and read in one Paper-thread batch. Manual progress bootstrap issues a non-serializable owner capability; provider/metric/generation-scoped handles and capability-attested provenance authorize bounded in-memory aggregation, versioned batch persistence, and flush/shutdown barriers. Human-readable owner identity is metadata only. | Avoids invented/invalid capabilities, main-thread/provider-call fan-out, spoofed API progress, registration races, unbounded caches, and SQL-per-event behavior. |
| D-047 | Phase 3 implementation | `requirements.yml`, `rewards.yml`, and schema-3 stage references compile through the existing canonical draft/revision workflow. One atomic `ActiveStageConfiguration` publishes same-revision Stage and Phase 3 snapshots, and the Phase 3 snapshot retains the exact active/referenced provider-generation map validated during prepare/apply, including configured rank projection. Runtime never reconstructs those pins from the mutable registry. Dormant definitions remain schema/type validated without activating providers; absent optional reward providers do not block apply or receive a pin. | Prevents a parallel configuration truth, mixed revisions, silently rewritten pins, eager dormant-provider coupling, and inconsistent optional-reward semantics. |
| D-048 | Phase 4 implementation | Prestige is a distinct intent-only authorization, immutable simulation, opaque authorization, plan, executor, and persistence lifecycle built over the shared operation journal; it is not disguised as a rank-up. | Prestige resets stage, scope, currency, milestone, and count state together and therefore has materially different confirmation, transaction, and recovery semantics. |
| D-049 | Phase 4 implementation | Prestige execution orders journal insertion → verified costs → configured managed-rank projection → one atomic internal commit → rewards. The internal transaction CAS-updates stage and current/lifetime Prestige, creates the next Prestige scope/baselines, resets configured internal currency, records milestone awards, and appends stage/Prestige history. | Required rewards are preflighted before mutation. External projection failure cannot produce false internal success; external success followed by failed/unknown internal commit and post-commit reward uncertainty are explicit reconciliation states. |
| D-050 | Phase 4 implementation | Every resettable component has an explicit `RESET`/`PRESERVE` classification. Stage resets and historical-statistics preservation are mandatory invariants; a successful Prestige creates a new immutable scope identity instead of deleting prior baseline/latch/history rows. | Old scoped state remains auditable but cannot leak into `SINCE_PRESTIGE_START`. External provider reset authority is separate, unsupported, and disabled in Phase 4. |
| D-051 | Phase 4 implementation | Internal currency uses stable `CurrencyId`, exact decimal text, bounded scale/precision/balance policy, transactionally maintained account plus append-only ledger, and unique operation/action idempotency. Cost and reward roles use separate providers because their Java batch interfaces erase to incompatible `List` signatures. | Display/symbol edits cannot rename data; no floating point, negative balance, unaudited adjustment, or replay double debit/credit is permitted. SQLite transactions/idempotency are authoritative; synchronization only reduces local contention. |
| D-052 | Phase 4 implementation | Entitlements are typed values with deterministic source ordering and explicit duplicate-source rejection. Built-in merge strategies are `MAX`, overflow-safe `SUM`, `MIN`, priority-ordered `OVERRIDE`, and `BOOLEAN_OR`, all returning source provenance. | Prevents map-iteration nondeterminism and accidental additive stacking when configuration intends a maximum. Provider-defined strategy extension remains unfrozen until the later SDK phase. |
| D-053 | Phase 4 implementation | Milestone identity and repeatability keys (`ONCE`, `ONCE_PER_PRESTIGE`, `ONCE_PER_SEASON`) are persisted in the same internal Prestige transaction. Prestige-count milestone rewards are folded into canonical preflight and the operation plan. | One-time awards cannot be redelivered after restart. Stage/season/provider trigger shapes are modeled, but their separate lifecycle award hooks are not falsely executed by the Prestige service. |
| D-054 | Phase 4 implementation | Seasons are optional one-active-at-a-time progression-data containers. Start allocates a new scope, player entry initializes real season baselines, end archives before a replacement can start, and reset/preserve of season progress is explicit. | SQLite uniqueness plus lifecycle compare-and-set protects the one-active rule; no world, PvP, Court, or resource-world ownership is implied. |
| D-055 | Phase 4 implementation | Startup recovery scans a bounded indexed set of incomplete operations and makes operation-type-aware decisions from persisted operation/action/internal-commit evidence. It verifies known internal effects without replay, abandons unexecuted prepared work, and marks interrupted or incomplete external effects uncertain/reconcilable. Recovery decisions are appended to their own audit table. | Exactly-once is claimed only for native transaction/idempotency effects. Unknown external effects are never blindly replayed or described as rolled back. |
| D-056 | Phase 4 implementation | Competition has a real disabled/default-off boundary. Unsupported enabled configuration fails validation and construction; no competition service, command, UI, lifecycle, or named legacy competition exists. | This satisfies disabled-behavior A34 without claiming the larger optional competition framework from Section 18. |
| D-057 | Phase 4 implementation | `lifecycle.yml` compiles through the existing immutable compiled-document boundary, Phase 4 extends the canonical schema, semantic validation checks stage/reward/provider references, and Phase 4 snapshots retain every prior provider-generation pin while allowing additional Phase 4 pins. | Preserves lossless draft/revision ownership and prevents a parallel ad-hoc runtime configuration or mixed provider generations. V2 remains deliberately unconnected to the frozen production bootstrap. |
| D-058 | Phase 4 correction | Prestige requirement progress, baselines, and latches form one coherent scoped-state disposition: all `RESET` creates a new scope and reachable boundaries; all `PRESERVE` retains the existing scope and writes no boundaries. Stage is reset-only; purchased perks, milestone history, season progress, and historical statistics are preserve-only. | Simulation and execution cannot diverge through contradictory or unimplemented component policies. Historical evidence is retained rather than deleted. |
| D-059 | Phase 4 correction | Phase 4 provider activation is reachability- and role-local. The enabled Prestige tree is traversed transitively, exact generations are pinned only for consumed providers, and planning plus post-cost execution require active healthy bindings. | Dormant/optional providers remain lazy, while a required reset-rank or boundary metric provider cannot yield an executable stale/unhealthy confirmation. |
| D-060 | Phase 4 correction | Native currency provenance is carried by sealed planned actions. SQLite transactions, uniqueness, and bounded whole-transaction contention retry are the cross-instance concurrency boundary. Season entry plus required baselines and normal rank-up stage CAS plus history each commit atomically. | Removes mutable-revision provenance and process-local concurrency assumptions, and closes the season/stage-history crash boundaries. |
| D-061 | Phase 4 correction | Recovery stores provider/action characteristics and exact sealed native cost/reward payloads. Only healthy generation-matching native recoverable providers may replay idempotent rewards or compensate known applied reversible/idempotent costs; unknown external actions remain uncertain. | A59 is supported without weakening A60 or fabricating a new plan after restart. |
| D-062 | Phase 4 correction | A16 and A17 remain `Partial`: engine + persistence lifecycle semantics are implemented and restart-tested, but production runtime composition remains later. | Applies the same project acceptance criterion already used for A14/A15 and avoids pulling later bootstrap work into Phase 4. |
| D-063 | Phase 4 correction pass 2 | Recovery may terminally declare `COMPENSATED` only after every potentially consequential cost action is proven absent or safely reversed. Safe native compensation may proceed while another `STARTED`/`UNCERTAIN` cost keeps the operation in `NEEDS_RECONCILIATION`. | Prevents a mixed native/external pre-commit crash from falsely claiming the whole operation was reversed; retry retains the evidence and never duplicates compensation. |
| D-064 | Phase 4 correction pass 2 | Season configuration models only its owned `SEASON_PROGRESS` disposition. The season YAML policy accepts exactly `season-progress: RESET|PRESERVE`; unrelated reset components are compiler errors. Player entry qualifies `ACTIVE` inside its write transaction, and progress mutation conditionally requires `ACTIVE` in the authoritative update. | Removes inert configuration, linearizes entry against archive, and makes archived history immutable while retaining exact reset/preserve carry-forward semantics. |
| D-065 | Phase 4 correction pass 2 | Currency operation/action replay equivalence binds player, currency, exact delta, mutation kind, configuration revision, actor type/UUID/name, source, and reason. Retry-only `occurredAt` does not participate. | The same idempotency key cannot relabel an audited mutation, while a legitimate later retry still resolves deterministically to the one stored effect. |
| D-066 | Phase 4 correction pass 2 | Stage-history actor UUID is nullable but durable. Migration 5 adds `actor_uuid`; both normal rank-up and Prestige-reset writers bind it, and reads reconstruct the complete `Actor`. | Full actor identity survives close/reopen without invalidating console/system rows that legitimately have no UUID. |
