BLOCKER 1 — STRICT CONFIGURATION SHAPES AND IDENTIFIERS
An optional mapping receives an empty/dormant default only when its field is absent. A
present mapping field with null, boolean, number, string, or sequence value is rejected.
The structured finding path names the exact object and the explanation identifies the
expected mapping and practical actual type. This rule covers vault, mcmmo,
placeholderapi, placeholderapi.output, placeholderapi.inputs, each input definition,
economyshopgui, both shop progression-credit objects, and quickshop. Unknown fields
remain errors. The schema now declares every Phase 5 mapping node explicitly.

Placeholder input keys must be actual YAML String keys. Numeric, boolean, null, and
object keys are never String.valueOf-coerced. Each string is constructed as the
canonical API MetricId before configuration is accepted; the exact offending input
path is reported on failure. Valid lowercase canonical IDs remain unchanged.

The same audit also corrected adjacent coercion defects: schema-version must be an
actual YAML integer, boolean fields must be actual YAML booleans, and positive
ISO-8601 durations report their precise field path. A compile error still returns only
the safe disabled fallback and cannot activate malformed HOT_RELOAD input.

BLOCKER 2 — EXACT PROVIDER LIFECYCLE RECONCILIATION
PhaseFiveIntegrationPlan exposes the exact reachable provider set.
IntegrationProviderLifecycle.reconcile(plan) applies that set authoritatively:
1. copy/validate the desired set;
2. inspect each owned discovered registration's current activation;
3. activate a desired inactive binding and mark it ACTIVE;
4. deactivate an active binding absent from the desired set and mark it INACTIVE;
5. do nothing to an unchanged desired active binding or unrelated dormant binding.

The old additive activateReferenced API no longer exists. Shrink, expansion, removal,
addition, and identical reapplication are deterministic/idempotent. Activation and
deactivation reuse the same registration/generation. Only dependency unregister plus
genuine discovery/rebind advances generation. An unrelated unhealthy dormant provider
does not block required reconciliation. A real compiled mcmmo-enabled plan followed by
an empty HOT_RELOAD plan proves active -> dormant removal without generation churn.

BLOCKER 3 — PLACEHOLDERAPI SELF-RECURSION
Validation scans every closed %identifier_parameters% token in each configured input.
It extracts the identifier before the first parameter underscore and compares it to
maddprestige case-insensitively, matching PlaceholderAPI expansion lookup semantics.
Lowercase, uppercase, title case, arbitrary mixed case, and a multi-placeholder string
containing a MaddPrestige token are rejected. Multiple external tokens are accepted.
%someplugin_maddprestige_value% is accepted because its expansion identifier is
someplugin; the similar text occurs only in parameters. The finding identifies the
exact input placeholder path. Requirement reads remain cache-only and zero-mutation.

BLOCKER 4 — ECONOMYSHOPGUI FINAL DECISION
EconomyShopGUI progression is deferred. The verified public 1.10.1 PostTransactionEvent
contract remains as an optional/default-off compatibility diagnostic listener only.
It has no MetricProvider, CostProvider, RewardProvider, ManualMetricHandle, amount
conversion, or persistence path, and progressionCredits() is hard zero. Configuration
has separate compatibility-enabled and progression-credit.enabled fields; progression
accepts only false and true fails actionably.

The withdrawn sale metric used scalar getPrice() and could not truthfully distinguish
Vault money, EXP, levels, item currencies, PlayerPoints, or custom economies, nor every
total in multi-economy sale events. No giant multi-currency subsystem was pulled into
Phase 5. A later currency-aware provider design is required before progression support
can be claimed.
