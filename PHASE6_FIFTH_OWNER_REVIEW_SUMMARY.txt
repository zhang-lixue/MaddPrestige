ARCHITECTURE

Durable owner identity
  The exact candidate revision's ATTEMPTED mp_configuration_revisions_v2 row is the owner. Parent revision and canonical candidate hash must match. The existing configuration history is reused rather than creating a competing owner journal.

Durable evidence and scope
  Migration 10 adds mp_configuration_stage_transitions, immutable mp_configuration_transition_stages and active mp_configuration_stage_reservations. Each declared stage is REMOVED, DISABLED or legacy UNKNOWN_LEGACY. Normal acquisition requires complete exact scope and bidirectional declared/active reservation equality.

Acquisition ordering
  ConfigurationAdministrationService appends ATTEMPTED history and prepares/verifies the immutable snapshot. PhaseSixConfigurationWorkflow then computes all removed/disabled stages. SqliteStageReferenceMigrationStore.beginTransition opens BEGIN IMMEDIATE; deletes only terminal operation leases; validates the exact history owner; rejects another unresolved configuration transition; rejects any operation lease whose source or target intersects the unsafe set; inserts transition, declared scope and reservations; revalidates every unsafe-stage count and the exact sealed remap rows; then performs all CAS row/history/remap writes before commit. Pointer and runtime activation occur only after this authority exists.

Why the zero-reference race is closed
  A zero-reference D receives an active reservation in the same transaction that proves its count is zero. Direct stage writers and operation lease acquisition also use BEGIN IMMEDIATE and consult that reservation before mutation/effects. They must serialize before or after acquisition: a writer that wins changes the authoritative count and causes final acquisition revalidation to fail; configuration that wins blocks the writer.

Operation-lease interaction
  Operation leases and configuration reservations remain distinct. An operation journal owns exact source/current plus target/result participation, token and restart lifecycle. A configuration revision owns the full set becoming unreferenceable. Both use the same SQLite serialization. Intersecting ownership fails closed; unrelated operations remain allowed.

Fallback-target invariant
  StageChangeImpactAnalyzer.coversAffected checks the server-owned compiled prior and candidate configurations, not mutable caller claims. Target existence, enabled state, ordering and exact internal/external projection semantics must be valid in both. Normal apply and rollback use the same analyzer. Candidate-only targets are intentionally unsupported because Phase 6 does not introduce inverse migration.

Release and recovery ordering
  Success publishes candidate pointer/runtime, records durable APPLIED history, then atomically marks CONFIG_APPLIED, updates a linked remap and removes reservations. Safe failure retains/restores prior pointer/runtime, records durable FAILED history, then releases as CONFIG_FAILED_SAFE. Pointer restore failure, pointer/runtime disagreement, incomplete scope or contradictory history stays NEEDS_RECONCILIATION and reserved. ConfigurationAdministrationService.recoverConfigurationStageTransitions compares history, filesystem pointer and canonical runtime; it never uses elapsed time. Terminal cleanup is idempotent and requires matching durable terminal history.

Malformed/orphan handling
  Incomplete scope, a missing or extra active reservation, missing/terminal history for an active transition, ownerless legacy pending remap, terminal transition with lingering reservation, and UNKNOWN_LEGACY scope fail globally closed. Doctor reports exact revision, scope kinds, lifecycle and owner status. Healthy complete short-lived authority is WARNING; contradictions and unresolved recovery are BLOCKED.

   Creates no player-stage rewrite. It resolves reservation lifecycle only from exact history/pointer/runtime coherence.

DETERMINISTIC RACE RESULTS

Operation wins
  Existing source or target participation makes configuration acquisition fail before migration/activation. Covered for rank-up target, projection target and Prestige/source participation, plus store-level source/target roles.

Configuration wins
  Zero-reference source/target reservation blocks rank-up before cost/projection/reward; blocks Prestige before cost/reset projection/reward; blocks standalone projection before adapter effects; and blocks direct insert/import/CAS/history/reset before durable write.

Zero-reference removal and disablement
  Both use identical authority. Direct writes losing to the reservation fail; a direct write winning first causes exact final revalidation to fail. An unrelated write/operation remains allowed.

Mixed candidate
  B referenced/remapped B→C, D zero-reference disabled, and F referenced/remapped F→E produce one B/D/F scope and one atomic remap. No source authority releases before configuration resolution.

Direct writes
  insert, importOnce, update and updateAndAppendHistory are covered. Source is selected inside the write transaction. No check→write gap or unjournaled durable lease exists.

Rollback
  Rollback rejects a candidate-only fallback target, accumulates multiple source mappings, reserves referenced and zero-reference unsafe stages together, and uses the same activation/recovery path as normal apply.

Two configuration drafts
  A second unresolved destructive transition fails before creating conflicting reservations, including when its stages do not overlap. Retry cannot adopt terminal/NEEDS authority as a fresh ATTEMPTED transition.

RECOVERY RESULTS

Covered crash/evidence boundaries include:
  - after reservation/remap and before activation: prior pointer/runtime coherence records FAILED and releases safely;
  - after prepared candidate snapshot but before pointer switch: the same prior-authority resolution applies;
  - after pointer switch with runtime activation failure and successful prior-pointer restoration: FAILED history precedes CONFIG_FAILED_SAFE cleanup;
  - after pointer restoration but before reservation cleanup: restart recovery completes only from FAILED+prior coherence;
  - after APPLIED terminal history but before cleanup: recovery releases only when pointer and runtime both equal the candidate;
  - pointer/runtime mismatch or failed restore: authority remains NEEDS_RECONCILIATION across reopen;
  - legacy unknown complete scope: globally fail-closed and Doctor-visible;
  - partial declared/active scope and terminal owner with lingering authority: globally fail-closed and diagnostically abnormal;
  - repeated/concurrent terminal release: idempotent.

No reservation is deleted based on age. No orphan is treated as safe. Unresolved ownership prevents unsafe writes until authoritative evidence changes.
