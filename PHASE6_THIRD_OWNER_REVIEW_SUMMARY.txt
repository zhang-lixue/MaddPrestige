STAGE TRANSITION FENCE ARCHITECTURE

SQLite migration 8 adds mp_stage_transition_leases with exact operation ID, target stage, configuration
revision and acquisition time. SqliteStageReferenceMigrationStore implements both StageReferenceMigrationStore
and the canonical StageTransitionFence. Lease acquisition and remap migration begin with BEGIN IMMEDIATE.

If an operation lease wins first, a destructive remap targeting that stage fails before snapshot
revalidation or row movement. If remap wins first, the committed MIGRATED_PENDING_CONFIG operation plus its
exact source-stage entries durably rejects new target-stage leases. The remap journal, not process-local
memory, fences the SQL-commit-to-pointer/runtime-activation interval and survives restart.

Exact stage-mutating gate points:

- RankUpOperationExecutor: after canonical authorization/config/provider checks, before duplicate lookup,
  operation insertion, costs, external projection, stage commit and rewards.
- PrestigeOperationExecutor: after canonical authorization/config/provider checks, before operation insertion,
  costs, reset projection, lifecycle/current-stage commit and rewards.
- RankProjectionOperationExecutor: before operation insertion and before the external RankAdapter call.
- SqlitePlayerStageRepository: before insert/import, update and update-plus-history; executor commits re-enter
  the exact operation lease, while direct/manual calls acquire their own lease.
- SqlitePrestigeLifecycleRepository: before reset-stage/current-state commit and re-enters the executor lease.
- SqliteStageReferenceMigrationStore: checks all leases before exact remap revalidation and row migration.

Terminal operation outcomes release newly acquired leases. NEEDS_RECONCILIATION/uncertain outcomes retain
their lease, with the operation journal as the recovery authority. Calls resuming the same operation/target/
revision re-enter rather than creating competing authority. No late-write-only check is relied upon.

STALE AUTHORIZATION, RACE AND RECOVERY RESULTS

The deterministic integration pause occurs after B→C SQL migration commits but before the configuration
pointer/runtime leaves R1. At the pause, R1 still contains B and all migrated rows are already C. A restarted
fence instance and the direct/manual player-stage repository both reject a new B reference. Real durable-
journal executor tests use plans authorized before the fence and prove rank-up and Prestige reject before
operation persistence, cost, projection, internal commit or reward. After resume, R2 contains A→C, all
affected rows are C, and the queryable current-stage state contains zero B references.

Crash/restart behavior: MIGRATED_PENDING_CONFIG and source-stage entries remain durable, so reopening the
database cannot forget the barrier. CONFIG_APPLIED is terminal after new pointer/runtime authority.
CONFIG_FAILED_SAFE is terminal only when old pointer/runtime authority is known retained/restored and all
migrated references point to a projection-equivalent replacement valid there.

Additional recovery defect found and fixed: if runtime publication fails after pointer selection and restoring
the previous pointer also fails, the code no longer marks CONFIG_FAILED_SAFE. It leaves
MIGRATED_PENDING_CONFIG intact. A regression proves the pointer/runtime mismatch remains fenced across
restart and requires explicit reconciliation. This is coordinated cross-store safety; no SQLite/filesystem/
runtime atomic-transaction claim is made.

IMMUTABLE DRAFT APPLY PROVENANCE

Draft kind is assigned only at server-side creation and cannot change:

- NORMAL -> CONFIG_APPLY (maddprestige.admin.config.apply)
- ROLLBACK -> CONFIG_ROLLBACK (maddprestige.admin.config.rollback)
- SETUP -> SETUP (maddprestige.admin.setup)

Preview, acknowledgement preparation, acknowledgement confirmation, direct/command/GUI apply and final
mutation load the live draft and derive this exact kind. Public acknowledgement accepts no caller kind.
Cross-kind direct methods reject config.apply.kind_mismatch. Finalization rechecks current matching permission
after asynchronous preparation and immediately before draft claim/durable work.

Tests prove normal drafts cannot use rollback authority, rollback drafts cannot use normal authority, setup
cannot cross kinds, all correct flows work, permission revoked after acknowledgement blocks mutation, wrong
actors cannot consume authority, replay fails, and exactly one concurrent confirmation succeeds. Correction
Pass 2 also made consumed acknowledgement classification deterministic for racing/replayed callers with a
bounded five-minute tombstone, preserving one-winner behavior without retaining usable authority.
